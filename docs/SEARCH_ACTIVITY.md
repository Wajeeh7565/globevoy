## What already existed

## Components and boundaries
- backend/services/analytics/search-activity.js: wrap invokes the original public handler once, then records completion without changing its body/status or existing headers. Successful recording adds X-GV-Activity-Id, a non-identifying per-request hash, to correlate real acceptance; no user/session identifier is added. configuration validates an opt-in nonsecret build file. sanitize produces only schemaVersion, random/server-request-derived eventId, UTC date, category, outcome, result-count band, duration band, price-evidence category and TTL. persist atomically inserts the unique event and increments one counter. No user ID, guest cookie, session ID, headers, IP, travel dates/airports, queries, budgets, credentials or raw error messages are stored.
- backend/lambda.js: one wrapper at the public API boundary. Categories: recommendations, mixed_results, multi_city, generated_tour, date_adjustment, route_adjustment, fare_calendar, flex_windows, one_way_lookup. frontend/runtime/api-client.js and web/lib/api.ts use these public endpoints; legacy explorers also use fare-calendar/flex-windows. Auxiliary lookups/adjustments have separate categories: do not sum them into the count of initial customer searches. Internal generation/provider function calls do not emit separate events. OPTIONS, admin, registry, account/login and unknown routes are excluded.
- production-account-lambda.js forwards actual Lambda invocation context only for public delegation; private auth and ownership remain unchanged. No token is needed for guest analytics.
- Events use PK DAY#YYYY-MM-DD and SK EVENT#hashed-server-request-id. Counter rows share the day and use COUNT#category#outcome. A conditional event insert and counter update are one transaction: replay cannot increment the count twice. Different HTTP invocations, including browser retries, are distinct events. There is no cross-device/user tracking.
- Price category is conservative: LIVE requires explicit production eligibility and unexpired evidence, otherwise not_assessed; other categories include cached, estimated, unavailable and mixed. A mixed flight/hotel price cannot become a full-trip LIVE claim. No inference from mere provider names. No prices are stored.
- ops/analytics/daily-counts.py: local AWS-IAM-authenticated, consistent Query of COUNT# rows for one UTC day, no scan or public endpoint. Reader policy is separate from the Lambda writer. The operator policy may also inspect approved sanitized event rows with a day Query for acceptance; it has no account-table access.

## Reliability and limits
SDK maxAttempts=1, 200 ms AbortSignal deadline, skip if less than 400 ms invocation time remains, catch all analytics/config/logging errors and preserve the original search response/exception. Fixed operational log records contain only component/status. Event and counter writes commit together or not at all, including ambiguous network failures. DynamoDB may finish a timed-out transaction: use its event ID to inspect, not an unconditional retry. Duplicate transaction cancellation cannot double-count. This is best-effort analytics, not guaranteed-lossless delivery during outages; searches take priority. SDK startup overhead and response parsing add small unmeasured CPU cost; the deadline bounds the network operation, not every CPU instruction. No background fire-and-forget Lambda writes.

TTL is eventual, not an exact-time deletion guarantee. Query counts only within the approved retention window; administrators must not promise exact-time erasure. Counters may outlive the first event in a day by less than a day. One per-category/day counter can contend at high rates; this scope targets current small beta traffic, not unbounded high-volume analytics. Monitor write failures and throttle alarm; shard only if measured traffic requires it.
